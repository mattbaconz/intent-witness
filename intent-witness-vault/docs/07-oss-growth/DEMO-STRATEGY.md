# Demo Strategy

## The demo must prove mechanism, not just outcome

A static before/after can be accused of cherry-picking. The best demo shows the review interruption.

## Ideal 15-second sequence

```text
0–3s   Agent-generated dashboard appears.
3–6s   Intent Witness: REVISE — primary workflow buried under generic metric grid.
6–10s  Agent restructures around primary domain object.
10–13s New UI appears.
13–15s Intent Witness: PASS_WITH_NOTES.
```

Overlay:

> Same model. Same brief. Independent design review.

## Demo case selection

Use a product where generic UI is visibly inappropriate:

- agent orchestration/operations;
- incident response;
- unusual creative workflow;
- domain with meaningful state/urgency.

Avoid only landing pages; competitors already excel there and aesthetic preference dominates.

## Proof package

For each flagship demo publish:

- exact task brief;
- model/ADE version;
- baseline configuration;
- initial/final screenshots;
- reviewer result;
- relevant code commits if practical;
- limitations.

## Bad demo

Before: intentionally hideous purple cards.
After: polished dark Linear-like UI.

This proves taste curation, not Intent Witness.

## Good demo

Before: attractive but structurally generic.
After: similar visual quality, but hierarchy/IA now maps clearly to domain workflow.

## Comparative demo

Eventually show four outputs:

```text
Vanilla
Strong prompt
Competitor skill
Intent Witness
```

Do blind community voting before revealing labels.

## Viral phrase candidates

- “I gave my coding agent a design reviewer.”
- “Your agent isn’t done because the UI compiles.”
- “Same model. Same brief. One was allowed to self-review.”

Use responsibly; do not overstate benchmark conclusions.
